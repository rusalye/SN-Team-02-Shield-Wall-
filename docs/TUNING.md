# Tuning notes

Goal: block 100% of the attack replay while allowing at least 95% of the benign replay (the benign client's 27 requests; one false positive is already 96.3%, but the target is zero).

## 1. Workflow

1. Start in **detect** mode so nothing is blocked while you look: `make mode-detect`.
2. Run the benign traffic: `make benign`.
3. List which rules *would have* matched the benign client. In detect mode a request is not blocked, so `make fp` (which filters on blocked events) shows nothing. Use the unfiltered query instead:
   ```bash
   curl -s "http://127.0.0.1:9000/api/events?ip=172.28.0.101&limit=100" \
     | python3 -c "import sys,json;[print(e['method'],e['uri'][:70],e['rules'],e['score']) for e in json.load(sys.stdin) if e['rules']]"
   ```
4. For each hit decide: is it a **real** attack signal or a **false positive**? Only add an exclusion for false positives.
5. Add the narrowest exclusion possible (see section 3), then `make mode-on`, `make unban`, and re-run `make benign` and `make attack`.
6. When a benign request is blocked in `on` mode, `make fp` lists the blocking rules directly.
7. Record the change in the tuning log (section 5).

## 2. Knobs, from least to most invasive

| Knob | Where | Effect | When to use |
|---|---|---|---|
| Exclude one **target** from one tag or rule | `rules-before/10-juiceshop-exclusions.conf` | Removes e.g. the `token` cookie from SQLi checks only | First choice for every false positive |
| Exclude one rule on one **path** | same file, scoped with a path condition | Narrow scope | When the target exclusion is not enough |
| `INBOUND_THRESHOLD` | `.env` | Raises or lowers the score needed to block | Last resort; weakens every rule |
| `PARANOIA` | `.env` | PL1 to PL4 | Only to trade coverage for noise globally |
| `LOGIN_RATE`, `LOGIN_BURST` | `.env` | Brute-force sensitivity | If real users are throttled |
| `BAN_STRIKES`, `STRIKE_WINDOW`, `BAN_STEPS` | `.env` | Sentinel ban sensitivity | If a benign client is auto-banned |

Rules of thumb: never disable a rule globally, never exclude a whole URL from inspection, and keep every exclusion commented with the reason.

## 3. Exclusions currently in place

| ID | Scope | Reason |
|---|---|---|
| 1000100 | Targets `REQUEST_COOKIES:token`, `REQUEST_COOKIES:continueCode`, `REQUEST_HEADERS:Authorization` for all CRS rules | JWTs and continue codes are base64 with `=` and `.` characters that resemble SQLi and XSS patterns. They are generated by the server and signed, so inspecting them for injection adds noise but no protection. |
| 1000002 | Allowed methods extended to include `PUT`, `PATCH`, `DELETE` | Juice Shop's REST API uses them legitimately. |
| 1000003 | Allowed content types extended with `application/json` and CloudEvents variants | The CRS default list is narrower than a JSON API needs. |
| 200000-200006 | JSON and XML request body processors | Without them JSON bodies are not parsed, so payloads inside JSON keys and values would not be inspected at all. This is a protection feature, not an exclusion. |

## 4. Why some choices are not "tuning"

* Honeypot paths and virtual patches are not CRS tuning. They are deny rules that run before CRS.
* The `SecAuditLogRelevantStatus "^(?:5|4(?!04))"` setting records every 4xx/5xx except 404 so Sentinel sees blocks without being flooded by scanner 404s.

## 6. Judge-proofing

Judges may run variations of the attack script. Before the event, send three or four of your own variants per class (different encodings, other tables, other shells) and confirm they are blocked; commands are in [TESTING.md](TESTING.md). If a variant slips through, prefer fixing it with a narrowly-scoped custom rule over lowering the threshold.
